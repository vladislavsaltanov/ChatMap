# Дизайн: двухпроходная статистика + таймлайн-лента

Статус: утверждён 2026-11-18. Приоритет владельца: «красиво и информативно-правдиво» —
каждое число ленты выводится из реальных данных чата (префиксные суммы частот,
реальные счётчики сообщений), визуал — только в существующем дизайн-языке.
Спроектировано поверх спайка
`specs/archive/spikes/SPIKE-load-pipeline-bench.md` (замер на реальном экспорте
23.1 МБ / 58k сообщений: конвейер open ≈ 3.7 с, из них tally 3.0 с; куча 1.4 ГБ;
1.9M записей пар, из которых полезны ≤ 10k рёбер между ≤ 600 словами).

## Решения пользователя (2026-11-18)

1. Раскладка — **пин**: считается один раз по всему чату, при скрабе меняются
   только размеры/цвета/рёбра, слова не двигаются.
2. Дефолт ползунка — **вся история** (правый край); лента показывает, как
   «росла» итоговая карта.
3. Таймлайн — **opt-in**: без включения поведение карты байт-в-байт сегодняшнее.
4. **Правдивость визуала (2026-11-18):** размеры нод пересчитываются по срезу
   (никаких замороженных итоговых размеров), полоса активности = реальное число
   сообщений в бакете, подпись курсора — реальные числа среза; никаких
   сглаживаний и приближений, выдающих себя за данные.

## Intent

Одна структура данных закрывает обе задачи:

- **Загрузка:** open ≈ 1–1.5 с вместо 3.7 с, куча ~300–400 МБ вместо 1.4 ГБ
  (проход 2 не материализует 1.9M PairStat).
- **Лента:** срез «с начала до момента T» собирается из префиксных сумм
  (частоты) + ограниченного скана (рёбра между словами топа среза), а не из
  полного пересчёта.

Кандидат A из спайка (плоский стор для ВСЕХ пар) **отвергнут**: он ускоряет open,
но не даёт дешёвых срезов по времени — под требование ленты это частично
выброшенная работа.

## Ядро: двухпроходная tally с бакетами по времени

### Проход 1 — частоты по бакетам (при open, один раз)

- Бакет = месяц; если весь чат короче 6 месяцев — неделя; короче 2 недель —
  один бакет (лента вырождается и отключается).
- На выходе: `token × author × bucket → count` (разреженно: у большинства
  токенов 1–2 автора; `Map<tokId, Map<authorId, Uint32Array(buckets)>>`).
  Память на реальном файле ≈ 24.5k токенов × 2 × 40 × 4 Б ≈ 8 МБ.
- Частота слова на срезе = сумма бакетов `[0..T]`; окно `[A..B]` = разность
  префиксов (запас на будущий режим «окно», в v1 не строим).
- Сообщения с `dateMs <= 0` (нет даты) — guard: считаются в бакет 0
  («всегда включены»), порядок сообщений не важен.

### Проход 2 — рёбра только между словами топа среза (по запросу)

- Членство: множество id топ-N слов среза (N = ViewCfg.topN, дефолт 600),
- Сканируем юниты чата; юниты из бакетов `> T` пропускаются; пары копятся
  только для пар, где оба токена в множестве. Метки `isCross` — как сегодня.
- Оценка на реальном файле: 0.1–0.5 с на срез (ранние срезы дешевле,
  полный срез ≈ один скан всех юнитов).
- Эквивалентность: для T = «вся история» результат обязан совпадать с
  сегодняшним `tally + select` на фикстурах —property-тест (двухпроходная
  равна однопроходной на полном срезе) — главный quality-гейт фазы 1.

### Пин раскладки

- Множество узлов ленты v1 = **топ-N всего чата** (те же слова, что и на
  итоговой карте). Слова, важные только в ранние периоды, на ленте не
  появляются — задокументированное огранишение v1; вариант «объединение
  топов по бакетам» (±1.5–3k узлов) — v2, он дороже раскладкой (солвер
  O(N²): 3k ≈ 9× бюджета S9).
- Воркер сохраняет результат полного layout (positions/ports/groupOf/stemOf)
  для пересчёта геометрии срезов: рёбра среза получают те же тракты
  (`bundleEdges` по пин-позициям), меняются только веса/альфа/видимость.
- Backbone среза пересчитывается по весам среза (дёшево: ≤10k кандидатов);
  геометрия новых рёбер — по тем же пин-портам.

### Режимы

- `together`/`author` — работают из коробки (частоты и nX из прохода 1/2).
- `cross` — один доп. ограниченный скан-битсет «у слова есть cross-пара»
  (без материализации пар), ~+0.3 с на включение режима. Не блокер.

### Протокол воркера

- `timelineOn` → воркер отвечает метаданными ленты: границы/метки бакетов,
  суммарные counts по бакетам (для мини-графика активности на полосе).
- `slice {bucket}` → `{type: 'slice', nodes: counts+authorLead, edges}` —
  только дельта к пин-карте; main применяет к существующему графу
  (обновление атрибутов + refresh, твины на рост/угасание существующие).
- Очередь срезов: main шлёт следующий `slice` только после ответа на
  предыдущий; промежуточные положения ползунка выбрасываются
  (latest-wins). Debounce ползунка ~150 мс.

### UI

- Кнопка «Таймлайн» (панель «Параметры», рядом с «Подсказка на карте»);
  полоса внизу канвы: месяцы, метки года, заполнение = активность чата.
- Взаимодействие: drag ползунка; тоггл фильтров при активной ленте —
  проход 2 перегоняется с новым cfg (кеш фильтров для прохода 1 не меняется).
- Стили: существующие токены CSS, без новых зависимостей, без градиентов.

## Фазы

- **Фаза 1 — фундамент (без UI):** двухпроходная tally + бакетированные
  частоты; открытый чат строится через новый путь. Гейты: property-эквивалентность
  на фикстурах; open ≤ 1.5 с / куча ≤ 400 МБ на 23 МБ профиле (замер
  `bench-tmp-load.test.ts`); существующие тесты tally/select зелёные.
- **Фаза 2 — лента:** протокол `timelineOn/slice`, полоса, пин-анимации,
  latest-wins, cross-битсет. Гейты: срез ≤ 400 мс p50; ручные браузерные
  кейсы (вкл/выкл ленты, скраб, смена фильтра при активной ленте).
- **Фаза 3 (опционально):** режим «окно за N месяцев», объединение топов
  по бакетам (v2 множества узлов).

## Non-goals

- Релеклаут на срез (отвергнут пользователем), per-message гранулярность,
- streaming-парсер JSON (94 мс — не цель), новые зависимости, сеть,
- изменения раскладки/рендера вне протокола срезов.

## Риски

- Расползание семантики двух проходов ↔ старой tally — закрывается
  property-тестом на всех фикстурах (sample-export, megahub, синтетика).
- Память на чатах с 20+ активными авторами — разреженное хранение авторов,
  замер на синтетике в фазе 1.
- Лента + smartMerge: склейка меняет id → срезы считаются в терминах
  корневых id (merge-отображение применяется до прохода 1), порядок
  фаз сохранить.
