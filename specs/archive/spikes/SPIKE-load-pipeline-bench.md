# Spike: load-pipeline bench на реальном экспорте

## Question

Где уходит wall-clock при открытии реального экспорта Telegram (23.1 МБ,
`result.json` из AyuGram) в конвейере decode → JSON.parse → parse() →
tokenize+intern → tally → select, и какая стадия доминирует? Нужно до решений
об оптимизации: прошлый perf-pass (A, 2026-11-09) целся в update-цикл и раскладку,
начальный open на реальных данных не мерился никогда.

## Method

Одноразовый замер `tests/bench-tmp-load.test.ts` (gitignored `tests/bench-tmp*`,
запуск только с `CHATMAP_BENCH_FILE`; vitest 5 прячет console прошедших тестов —
`--disableConsoleIntercept`). Node 22, тот же V8, что в воркере браузера.
Одна прогонка, без `--expose-gc` (числа округлены до мс).

## Numbers (23.1 MB → 58 005 сообщений, 2 автора)

| Стадия | Время |
|---|---|
| readFile | 7 ms |
| decode utf8 | 14 ms |
| JSON.parse | 94 ms |
| parse() (вкл. свой JSON.parse) | 123 ms |
| resolve: tokenizeChat + countSurfaces | 225 ms |
| resolve: addUnits + intern + **tally** | **3 182 ms** (tally отдельно: 2 998 ms) |
| select top-600 | 189 ms |
| **Итого конвейер (без раскладки/рендера)** | **≈ 3.7 s** |

Куча: 12 MB → 100 MB (parse) → **856 MB (resolve)** → 1 404 MB к концу.
RSS 1.6 GB. Словарь: 145 903 токена, 37 000 поверхностей, 24 552 канона.
**pairs = 1 912 336 записей.** Селекция: 595 узлов, 10 000 рёбер (cap MAX_EDGES).

## Learnings

1. **Tally — 88 % времени загрузки.** Decode+parse+JSON = 137 ms — трогать
   нечего. Tokenize (225 ms) и select (189 ms) — мелочь.
2. **Материализуется 1.9M PairStat, используется ≤ 10k рёбер между ≤ 600
   словами** — 99.5 % парной статистики строится и выбрасывается.
3. **Каждая пара = объект + вложенный `Map` (nX) + записи** ≈ ~400 B →
   ~760 MB аллокаций (совпадает с прыжком кучи на resolve). Chat с 2 авторами
   держит 1.9M Map'ов по ~2 записи — чистый GC-мусор.
4. `seenStamp`/`seenReplyStamp` — ещё два Map'а, растущих до ~1.9M ключей
   (запись на каждую window-new пару).
5. **Стена масштаба:** pairs ∝ сообщения × плотность. 100 МБ экспорт (~250k
   сообщений) → ~8M пар → ~6 GB кучи → OOM воркера, не «медленно», а крах.
   Сегодняшний дизайн деградирует квадратично по памяти на больших чатах.
6. Итерация без аллокаций дешева: buildUnits (tokenize+intern по 58k сообщений)
   = 613 ms — значит чистые циклы tally стоят ~300–500 ms, остальное —
   аллокации и GC.

## Candidate directions (для plan-work, НЕ реализовано)

- **A. Плоское хранилище пар** (сохранить архитектуру): `Map<edgeKey, index>`
  + `Float64Array`(nCross, nX-слоты на фикс. число авторов, overflow — в side-Map
  для чатов с >4 авторами на пару). Оценка: tally 3.0 s → 1.0–1.5 s,
  куча 1.4 GB → ~300 MB. Кеш/view-переключения остаются бесплатными.
- **B. Двухпроходная tally по селекции**: сперва только counts → top-N ids →
  второй проход копит пары только внутри селикшена (cross-режим: проход 1
  помечает только битсет «узел с cross-парой»). Максимальный выигрыш
  (→ ~0.5–1 s, ~150 MB), но topN/minWeight/mode-переключения перестают быть
  бесплатными (повторный ограниченный проход ~300–800 ms).
- Отвергнуто на спайке: streaming JSON-парсер (94 ms — не цель), правки
  decode/tokenize (мелкая доля), «оставить как есть» (OOM-стена на 100 МБ).

## Verdict

До A: полный open ≈ 3.7 s (на слабой машине 8–12 s), куча 1.4 GB на 23 МБ.
Оба кандидата требуют spec + TDD-план (tally — trust-boundary логика, 502-строчный
тестовый файл). Рекомендация: A как первый шаг (сохраняет семантику кеша),
B — вторым этапом, если A не даст достаточно.

Bench-файл оставить в `tests/bench-tmp-load.test.ts` (gitignored, безопасен
для дефолтного suite — skipIf без env) до закрытия оптимизации.
