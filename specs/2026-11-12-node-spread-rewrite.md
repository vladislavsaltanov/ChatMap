# Раскладка нод с нуля: «нейронная фигура» на прядях

Статус: `[STATUS: IN_PROGRESS — шаги 1–8 выполнены, остался скрин реального экспорта]`.
Дата: 2026-11-12. Заменяет собой: `2026-11-07-neural-bundles-plan.md`,
`2026-11-12-flow-figure-plan.md` (откачен), `2026-11-12-neural-lobes.md`,
`2026-11-12-multiphase-scatter-plan.md` в части *раскладки*. Не трогает парсер/токенайзер/тэлли.

## 1. Зачем

Сейчас позиция ноды = результат борьбы четырёх сил, которые гасят друг друга:
FA2 → `warpPlane` → `fractalClusterPlane` → `scatterLobes`/`scatterSublobes` →
`placeGroupsOnRing` → `fractalScatter` → солвер на 140–360 проходов. Каждый следующий
шаг существует, чтобы отменить побочный эффект предыдущего (handoff §4.2–4.3, §5).
Итог: карта читается как «облако с дырками», а не как орган.

Пользователь хочет: горизонтальная рваная фигура, нейронные ядра с отростками,
связи складываются в жгуты и расходятся из них (вода/ртуть) — и как следствие,
меньше визуального шума. Референсы: `photo_2026-11-12_00-59-46` (thunder, только
горизонтально), `photo_2026-11-03_18-25-56` (Colorpong neurones),
`824fc09bcded7e2cb6f834a2a9dd87cc` (Africa mesh), `44b281e12e612e52c7dbbbfe58a74cc4`
(ткань мозга, ч/б).

## 2. Что именно берём из референсов

| Референс | Что копируем | Чем это в коде |
| --- | --- | --- |
| Colorpong neurones | **ядро с снопом отростков**: у ядра жгут плотный, к концу прядь рассыпается, терминалы — точки на концах | посадка нод вдоль пряди с законом ширины `w(s) ∝ s^0.8` |
| Ткань мозга | длинные **изогнутые волокна** через весь кадр, а не лучи; ядра = сгустки на пересечении | изгиб пряди через curl-noise, шаг ≤ 0.5 рад |
| Thunder (гориз.) | **плотная голова + ствол + распыл + пыль**: закон плотности меняется вдоль фигуры | плотность вдоль пряди: туго у корня, распыл на конце; пыль отдельным пулом |
| Africa mesh | **линия = вес**: толстый ствол между массами, тонкие нити внутри | `corridorWeight` на маршруте ребра (жгут толще) |

Общее у всех четырёх: **нет единого центра**. Есть 3–7 ядер неравной массы, ствол
между ними и периферия-распыл. Одно-головую композицию (как на thunder) отвергаю:
у чата несколько тем, а не одна.

## 3. Границы

Цели:
1. Новый `spread` — присваивание позиций по структуре (ствол → ядро → прядь → нода),
   без «сил, которые борются».
2. Горизонтальный кадр: `spanX/spanY ∈ [1.55, 3.2]`.
3. Видимые пустоты между прядями (рваность) — не засыпаются солвером.
4. Детерминизм (тот же seed → те же координаты), инкрементальность по `prevXY`.
5. Маршруты рёбер по портам ядер: рёбра одного коридора **геометрически совпадают**,
   наложение даёт жгут.

Не-цели: таймлайн-слайдер, hover-веер, подписи/LOD, парсинг, стеммер, легенда,
новые зависимости.

Анти-цели (провал, даже если «красиво»):
- решётка/кольцо/луч-звезда (правильность видна глазом как регулярность);
- точка, где `spanX/spanY < 1.3` (квадрат);
- пустоты меньше 8 % bbox (каша);
- пересекающиеся тела (существующий гейт не ослабляется);
- раскладка «съедает» топологию: сильная связь дальше слабой.

## 4. Рассмотренные подходы

**A. «Колонизация пространства» (Runions 2007).** Аттракторы в поле плотности,
рост ветвей к их центроиду, убийство аттракторов у подошедшей ветви. Даёт буквально
морфологию нейрона и естественные пустоты. *Против:* позиция ноды перестаёт зависеть
от её темы — в алгоритме нет графа, только аттракторы; принадлежность к кластеру
придётся навязывать постфактум. Плюс O(N·A) и чувствительность к `d_i/d_k`.
**Не берём целиком, берём шаг роста пряди** (направление к аттракторам своего сектора).

**B. Нематическая среда (анизотропные пружины + curl-поле + дальнее отталкивание).**
Ближе всех к референсу «ткань», минимум нового кода поверх текущего солвера.
*Против:* это тот же класс решения, что сейчас — солвер; handoff §5 трижды показал,
что пустоты он перепаковывает, а градиенты просто сжимают ноды в максимумы.

**C. Прядевая раскладка (выбрано).** Позиция — *присваивание*: группа → ядро на стволе
→ прядь (изогнутая полилиния) → место на прядe. Пустоты появляются потому, что прядям
назначены разные секторы и между ними ничего не сажается; солвер в конце только
разнимает пересечения (ранний выход), а не перераспределяет. Рост пряди берём из A
(аттрактор своего сектора + curl + тропизм), посадку — из референсов 1 и 3.

Почему C: единственный подход, где форма — следствие структуры данных, а не
компромисса сил; и единственный, где маршруты рёбер можно сделать общими по
построению (порты ядер уже есть).

## 5. Конструкция

Новый модуль `src/core/spread.ts` (чистая логика, без graphology). `layout()` в
`graph.ts` остаётся единственной точкой входа для `worker.ts` и превращается в
адаптер ~40 строк.

### Шаг 0 — группы (`groupWords`)
Взвешенная label propagation по backbone-рёбрам: 6 проходов, порядок по весу ребра
desc, ничьи по id. Минимальный размер группы 4; одиночки без сильных связей → пул
`dust`. Выход: `groupOf: Map<id, group>`, группы сортированы по массе.
Детерминизм: фиксированный порядок обхода, seed не нужен.

### Шаг 1 — ствол (`placeTrunk`)
- `G = clamp(round(sqrt(N_clean) / 2.2), 3, 9)` ядер (N_clean = без dust).
- Порядок ядер — жадная цепочка максимальной аффинности: начинаем с тяжёлого, далее
  берём непомещённое с максимальной суммой веса к уже помещённым (переиспользуем
  идею `orderGroupsByAffinity`, код новый).
- Масса `m_i = members_i^0.62`; `x_i` распределены по `[-K, K]` пропорционально массе.
- `y_i = 0.30·K·fbm(x_i/K·π, seed)` + знакопеременный сдвиг `±0.06K` — ствол «дышит»,
  но остаётся горизонтальным.
- Радиус ядра `R_i = 0.075·K·sqrt(members_i)`; порт ядра `p_i = (x_i, y_i)`.
- Ствол = Catmull-Rom через порты в порядке цепочки. Это и есть маршрут для рёбер.

### Шаг 2 — пряди (`growStrands`)
Для ядра `i`: число прядей `A_i = clamp(round(3 + members_i/25), 3, 9)`.
- Сектор: нормаль ствола в точке порта, уводящая от глобального центроида; углы
  прядей разложены по массе (`m_j^0.5`), дрожание `±0.22` рад по `hash2`.
- Рост: `S = clamp(round(6 + members/6), 6, 22)` суставов, шаг `0.045K·(1+0.5·hash)`.
  Направление: `d ← normalize(0.55·d + 0.35·radial + 0.25·curl(x,y) + 0.15·awayFromNuclei)`,
  поворот за шаг ≤ 0.5 рад (защита от петель и шипов).
- Прядь не входит в диск чужого ядра (`R_j + 4·air`): при входе — отворот.
- Выход: полилиния с длиной `L_j` и накопленными аркдлинами. Группы крупнее 60 делятся
  на 2–4 подпряди (подъядро = своя короткая прядь от сустава).

### Шаг 3 — посадка (`embedMembers`)
Ноды ядра, кроме хаба, сортируются по весу связи с хабом.
- Назначение на прядь: минимизируем `(load_j + size_m) / m_j` — пропорциональный налив;
  если у ноды есть `prevXY` и кадр переиспользуется — побеждает прядь, чья осевая
  ближе к `prevXY` (стабильность кадра при фильтрах).
- Место: `s` растёт по аркдлине на `size·k + air_j(size)`; поперёк пряди
  `w(s) = (2.5·size + 4)·(s/L)^0.8`, знак по `hash2`. Туго у корня, распыл на конце.
- Ноды степени 1 сажаются последними — это терминалы на концах.
- Hub стоит в порту ядра.

### Шаг 4 — шлифовка (`roughen`)
Один проход доменного варпа вдоль нормали пряди: `amp = 0.02K·fractalNoise(id)`, затем
`resolveCollisions(...)` с бюджетом 28 проходов и существующим законом `airFor/dustTight`
(закон зазоров не меняется — он измерен). Пустоты к этому моменту уже заданы
присваиванием, солвер только разнимает.

### Шаг 5 — кадр (`fitFrame`)
Анизотропная нормировка: `spanX = max(6000, min(10000, sqrt(N)·320))`, `spanY = 0.52·spanX`,
центрирование. `squeezeTails`/`WARP_FIT_SLACK` не нужны: хвостов, которые «отбирают кадр»,
не существует по построению.

### Шаг 6 — маршруты рёбер (`routeEdges`, вместо `bundleEdges`)
Для backbone-ребра `(a, b)`, `ga = groupOf(a)`, `gb = groupOf(b)`:
- `ga === gb`: `c1 = lerp(a, port, 0.18)`, `c2 = lerp(b, port, 0.18)` — короткая дуга
  к своему ядру, локальное волокно.
- иначе: `c1 = lerp(a, port(ga), 0.72)`, `c2 = lerp(b, port(gb), 0.72)`. Для всех рёбер
  одной пары ядер `c1/c2` совпадают до поперечного сдвига `≤6 px` по рангу в коридоре →
  линии ложатся друг на друга и накапливаются в жгут (эффект воды), на подходе к ядру
  расходятся из одной точки (вытекают друг из друга).
- `corridorWeight` = число рёбер коридора; идёт в существующий шейдер как толщина.
Mean-shift по секторам (`SECTORS`, 3 прохода `bundleEdges`) удаляется: коридор теперь
известен из структуры, а не угадывается по геометрии.

### Инкрементальность
`cachedShare ≥ 0.6 && !fullRun` → переиспользуем порты/пряди, сажаем только новые ноды
к `anchorFor` (соседняя кэшированная нода). Иначе полный прогон.

## 8. Риски

1. **Label propagation на плотном графе даст одну гигантскую группу.** Митигация: работаем
   по backbone (Serrano, уже есть), ядро ограничено по массе (`members ≤ 0.35·N`), излишек
   раскидывается по соседним прядям как «сателлиты». Проверка — метрика размера групп.
2. **Реальный мега-хаб (85 % слов на одном слове).** Прядевая посадка делает из него одно
   ядро и обедняет карту. Митигация: жёсткий кап массы ядра + подпряди от его хаба.
   Единственный честный судья — скрин реального экспорта без ховера.
3. **Совпадение маршрутов = вспышка яркости.** Много рёбер в одном коридоре дают
   насыщенный белый жгут. Митигация: `corridorWeight` нормируется на `maxWeight`, шейдер
   уже умеет `strength`; проверить на 600 и 1000.
4. **Солвер всё ещё может выровнять пряди** в местах, где они близко. Митигация: секторы
   разведены по построению, бюджет проходов 28 вместо 140–360; мерить S2/S3 до/после.

### Что выяснилось при реализации (это дороже констант — не переоткрывать)

1. **Одна система единиц.** `size` ноды — экранные px. Spread считает в px и отдаёт
   координаты, `layout()` умножает их на `pxToWorld`. Смешение единиц давало зазоры,
   несовместимые с посадкой (первая версия: ядро 197 против слота 42).
2. **Никакой нормировки кадра.** Посадка идёт с реальным pitch; подгонка под фиксированный
   span делала pitch меньше зазора, солвер раздувал фигуру на 1.45× — незакрываемая петля.
   Размер фигуры — выход, а не вход: рендер фитит контент.
3. **Ширина ствола выводится из радиусов ядер.** Фиксированная ширина давала квадрат на
   600 нодах: 12 ядер радиуса 174 в слотах по 108 → солвер расходился по обеим осям.
4. **Плотность ограничена зазором.** Уплотнять ядро ниже clearance нельзя — солвер
   отыгрывает. Контраст покупается разрежением распыла (pitch ×6 к концу пряди).
5. **Пряди не могут стартовать из одной точки** — соседние первые места ближе зазора,
   солвер разносит их радиально и фигура вспухает. Нужен ступенчатый старт по радиусу.

### Что осталось (в порядке важности)

1. **Шаг 7: маршруты рёбер.** `bundleEdges` всё ещё считает mean-shift по секторам; линии
   поэтому не складываются в жгуты. Заменить на маршрут через порты (данные уже есть в
   `LayoutResult.ports` / `.corridors`).
2. **Ядра не читаются как узлы** на масштабе карты: контраст ядро/распыл есть (clump 13–17),
   но при 600 нодах и pitch ≈ 30 px ядро — это диск ~200 px, он сливается с соседним.
   Кандидаты: CORE_SHARE 0.55 → 0.7, ядер меньше при малой массе (3–5 вместо 9),
   радиальная упаковка ядра с переменным pitch.
3. **Аспект 271 = 1.38** ниже целевых 1.55: ядро доминирует по высоте. Связано с п. 2.
4. **Скрин реального экспорта** — стенд синтетический, он не показывает мега-хаб чата.

## 12. Шаг 7 + калибровка (вторая итерация, 2026-11-12)

**Маршруты рёбер.** Mean-shift по 8 секторам удалён из `geometry.ts` (−280 строк).
Теперь `bundleEdges(points, edges, _maxWeight, routes)` берёт `ports` и `groupOf` из

- внутри темы: тот же приём с `0.3` (короткая локальная дуга к соме);
- поперечный веер коридора `±6` world units по `tractRank`, поэтому жгут не становится
  одной волосинкой;
- `bundle` = размер коридора / максимальный, `rank` по весу, `tractRank` внутри коридора.
Рёбра одной пары тем получают одинаковые контрольные точки — это и есть геометрическое
слияние: кривые ложатся друг на друга и накапливаются (без шейдерной постобработки,
которой в Sigma 4.0.4 нет — проверено).

### Четвёртая итерация — изгиб и магистраль (по скрину 10:21)

Два разных дефекта по скрину:

1. **Изломы кривых.** `pathTract.segments` был 18 на кривую, которая может тянуться
